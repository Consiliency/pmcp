## Task

Consiliency/pmcp#338. The claude seat found it while reviewing
Consiliency/pmcp#337, the #298 implementation, and it is pre-existing on
main.

- **The cap is shared.** pmcp keeps at most 100 *finished* task records, and
  that one cap covers every server. A downstream whose tasks a caller lists
  can fill it and evict another server's finished tasks.
- **Unfinished tasks are not capped at all.** A downstream can keep any
  number of records alive by reporting `status: "working"`. Since #298 the
  same is true of a status pmcp cannot use, which is now recorded as `null`
  and so is never "finished".

The issue suggests the fix: a per-server cap covering finished and unfinished
tasks, eviction within that server first, and a global ceiling as a backstop.
Eviction stays in record order, as #337 established.

It also asks for **three wording corrections** to #337's CHANGELOG entry.
They are verified against the code in *Documentation impact*.

The brief adds four requirements:
- derive every record path from the code, not from the issue;
- prefer one choke point that every path goes through over a check on each
  path;
- add a structural guard if feasible;
- prove the patches embed.

### Every path that records a task (derived from the code)

`McpTaskRecord(` is constructed only there (`manager.py:1796`); `rg

### What hangs on a record (why eviction matters, and to whom)

Read from `manager.py` and `tools/handlers.py` on `31c1357`:

| Consumer | Uses the record for | When the record is gone |
|---|---|---|
| `cancel_task` (`:4109-4113`) | refuses without one | `(False, None, "Task not found: <server>::<id>")`. **Nothing is sent downstream.** |
| `disconnect_server` (`:1385-1398`) | refuses an unforced disconnect while `get_active_tasks(name)` is non-empty; a forced one sends `tasks/cancel` for each | not counted: not waited for, not cancelled |
| `cancel_active_tasks` (`:1865`) | same list | same |
| `get_task` / `get_task_result` (`:4051`, `:4076`) | reuse the stored `requestor_context` when the caller sends none | the downstream is still asked, without the stored context |
| `gateway.invoke` (`handlers.py:1664-1678`) | reads the record straight after `call_tool`; **default redaction is `task_info is not None`** | output is not redacted by default |
| `gateway.tasks_list` (`handlers.py:6021-6026`) | prefers the record | falls back to `McpTaskInfo(**task)` from the listing: no loss |
| `gateway.tasks_result` (`handlers.py:6118`) | `task` in the output | `task: null`; the result itself is unaffected |

Two consequences shape the design:
- **The record a path just stored must survive that same path.**
  `gateway.invoke` reads it back to choose its redaction. With "finished
  first", this is a real trap: a bucket of 100 `working` records receiving one
  `completed` would otherwise evict the new record, which is the only finished
  one.
- **An unfinished record carries behaviour, and a finished one carries a
  cache.** A finished record holds a final status the downstream still serves
  through `tasks/get`. An unfinished record is what `tasks_cancel`, the
  disconnect refusal and the stored `requestor_context` depend on.

## Design decisions (made explicitly)

### 1. One way in: `TaskRegistry.put`, a read-only mapping

The brief prefers removing the degree of freedom over checking each path.
Main already has a single writer (`_record_task`), but nothing keeps it
single. `_tasks` is a `dict`, so any new line `self._tasks[k] = v` would
bypass the cap silently, and mypy would accept it.

So `_tasks` becomes a `TaskRegistry`, in a new module
`src/pmcp/client/task_registry.py`:
- It is a `collections.abc.Mapping`: `[]`, `get`, `in`, iteration, `len`,
  `items`. Every existing reader keeps working unchanged.
- It has **no** `__setitem__`, `__delitem__`, `pop`, `popitem`, `setdefault` or
  `update`. A write that bypasses `put` is a mypy error (measured: `Unsupported target
  for indexed assignment`) and a `TypeError` at runtime.
- `put(record)` stores the record and applies both caps before it returns.
  The cap is not something a path can forget to call: storing *is* capping.
- `drop_server(name)` handles a disconnect and `clear()` handles shutdown.
  These are the two removals main already has.

`_record_task` stays the one function that builds a record and calls `put`.
It keeps its #298 field logic unchanged. The structural tests in Design
decision 7 pin both facts.

The registry is a class rather than a closure in the manager for three
reasons. It can be tested directly against a reference model
(`test_the_registry_matches_a_plain_restatement_of_the_rule`). Its mutable
surface is its type. And the manager loses the 30 lines of
`_evict_terminal_tasks`.

### 2. Per server: 100 records, finished and unfinished alike

Each server has its own bucket, capped at `per_server = 100`. That is main's
number: on main, 100 was the limit a single busy server could already reach
for finished tasks. A bucket over its cap gives up **its own** records and
nothing else, so no downstream can evict another's.

### 3. Victim order inside a server: finished first, then unfinished, each in record order

Decided: **finished first.** Inside the server being evicted from:
1. its oldest finished record (`completed`, `failed` or `cancelled`), if it
   has one;
2. otherwise its oldest unfinished record. Any other status counts as
   unfinished, including `None` and unknown future statuses.

"Oldest" means least recently recorded by pmcp. That is the record order
#337 established (`_recorded_order`, pmcp's own sequence). A re-record, such
as a `tasks_get` refresh, makes a task the newest again. No downstream
timestamp plays any part.

The argument comes from the consumer table in the research summary:
- A finished record is a cache. Losing it costs a caller nothing they cannot
  get back: `tasks_get` and `tasks_result` still reach the downstream, and
  `tasks_list` falls back to the listed payload.
- An unfinished record carries behaviour that silently stops when it goes:
  - `tasks_cancel` refuses without asking the downstream;
  - the disconnect refusal and the forced-disconnect cancel skip it;
  - the stored `requestor_context` is lost.
- Pure record order would let a burst of finished tasks push out older
  unfinished ones. That is exactly the work a caller may still need to
  cancel.

The cost: a server that holds a few long-running unfinished tasks and churns
many finished ones keeps its unfinished tasks longer than pure record order
would. That is the intent. It cannot be abused across servers, because the
bucket is the server's own. A server flooding its own bucket with unfinished
tasks only evicts its own records: after 500, it keeps the newest 100
(repro (b)).

**The record `put` just stored is never a victim of that `put`.** This is
needed by `gateway.invoke`'s redaction default (research summary). The
consequence: a bucket full of unfinished records that receives a finished one
evicts its oldest unfinished record, not the newcomer
(`test_the_record_just_stored_is_never_its_own_victim`,
`test_invoke_at_the_cap_keeps_its_record_and_redacts_by_default`).

### 4. The total: 1000 records, taken from the server holding the most

`total = 1000`, which is ten servers at their cap. It is a backstop for
memory: below it, the per-server caps decide everything. Past it, one record
goes:
- from **the server holding the most records**;
- on a tie, from the server whose next victim (by the rule in decision 3) was
  recorded first;
- never the record just stored.

Why this rule rather than "the globally oldest record":
- **The largest server pays first.** A server stays at or below the others'
  size, and so never loses a record to the total while a larger one exists.
  Before the total is reached, no server loses anything to another.
- **The two #337 cross-server tests keep their meaning under it.**
  - `test_one_downstream_cannot_keep_its_tasks_by_claiming_a_future_timestamp`:
    the liar has 2, the honest server 1, and the total is 2. The liar is
    the largest, so its oldest record, `b1`, goes.
  - `test_an_honest_server_with_a_slow_clock_keeps_its_newer_records`: one
    record each, total 1. The new record is never taken, so the on-time
    server's `a` goes.

  Both migrated to the total knob and pass without changing an assertion
  (measured).

The cost is an O(records) scan when the total is exceeded: one
`_candidate` pass per server. That is at most 1000 records, once per `put`
past the total. Below the total, `put` is O(bucket) ≤ 100.

The caps are attributes on the registry (`per_server`, `total`), not
configuration. Tests lower them. Making them operator-configurable is a
non-goal: no one has asked, and main had a constant. A cap below 1 is
refused with `ValueError`.

### 5. An evicted unfinished task: what the caller sees

Eviction forgets pmcp's record, not the downstream's task. Pinned by
`test_an_evicted_unfinished_task_is_re_tracked_by_tasks_get`:

| Caller action | Result |
|---|---|
| the call that created it (`gateway.invoke`) | already returned; its output was built while the record existed |
| `gateway.tasks_get` | still proxied to the downstream; the reply is recorded again, as the newest, which can evict another of that server's records |
| `gateway.tasks_result` | the same, through its `task` payload or its `tasks/get` fallback |
| `gateway.tasks_list` | lists it if the downstream does, and records it again |
| `gateway.tasks_cancel` | `ok=false`, `status: "not_found"`, `Task not found: <server>::<id>`, as for a task pmcp never saw. **Recovery:** call `gateway.tasks_get` first, then cancel (pinned) |
| `gateway.disconnect_server` | not counted as active: an unforced disconnect is not refused for it, and a forced one sends no `tasks/cancel` for it, because no snapshot holds it. **A stdio server's task ends with its process; a remote server's task keeps running** after the disconnect (rev 3, panel N1). Main's `_remove_server_indexes` docstring claimed "the downstream's tasks died with the connection", which is false for a remote server, and rev 3 corrects it. A record evicted *during* a forced teardown is different: the teardown still cancels it (Design decision 9) |
| a stored `requestor_context` | forgotten; the caller sends it again |

**Decided: `cancel_task` is unchanged.** It could forward an unknown task id
downstream instead of refusing. But that changes what `tasks_cancel` means
for *every* unknown id, not only evicted ones, and pmcp cannot tell "evicted"
from "never seen" without keeping tombstones, which is a second unbounded
structure. The recovery is one call, and the README now says so.

**The design removes the degree of freedom: one sender.** Rev 1 had two
teardown loops, each calling `cancel_task` and treating its refusal as
fatal. Rev 3 has one sender and one teardown helper:
- **`_send_task_cancel(server, task_id, force, requestor_context)`** is the
  only code that sends `tasks/cancel`; it records the reply. `cancel_task` is
  now its record check, "already terminal" or "Task not found", followed by
  `_send_task_cancel`. Its user-facing behaviour is unchanged (every existing
  `tasks_cancel` test passes).
- **`_cancel_tracked_for_teardown(snapshot)`** is the only code a teardown
  cancels through. `disconnect_server` and `cancel_active_tasks` pass it the
  active records they read. It does not call `cancel_task`, so "not found"
  cannot arise in a teardown at all.

`test_every_tasks_cancel_goes_through_the_one_sender` asserts three things:
- `_send_task_cancel` is called by exactly `cancel_task` and the helper;
- `cancel_task` is called only by `gateway.tasks_cancel`;
- the string `"tasks/cancel"` appears only in `_send_task_cancel`.

Mutants M25 and M26 restore rev 1's loops; both are killed.

**Rev 3 decision: an evicted snapshot task is cancelled, not skipped.** This
reverses rev 2. The panel's claude seat (round 2, N1) showed that rev 2's
reason, "the downstream's task dies with the connection", is false for a
remote server:
- `disconnect_server` only closes pmcp's transport (`_close_remote_transport`);
- no `tasks/cancel` goes out other than the cancel loop's.

A hosted tenant run on a remote server kept running after a forced
disconnect or restart that main would have cancelled. `f001.py` shows it:
main sends `tasks/cancel` for `['a', 'b']`, rev 2 for `['a']`. That is a
behavioural regression, not a wording problem.

So the helper cancels by the snapshot it was given. For each entry, after
re-reading:
- **tracked and finished meanwhile:** counted, nothing sent. This is the
  same as `cancel_task`'s "already terminal".
- **its server has no live connection** (rev 4 widens rev 3's "removed"):
  skipped; see "The no live connection rule" below.
- **otherwise, tracked or evicted:** `tasks/cancel` is sent through
  `_send_task_cancel`, with the current record's `requestor_context`, or
  the snapshot's when the record is gone *or has none* (rev 4).

**The context rule (rev 4, round-3 F001), fixed as a class.** A cancel
carries the best `requestor_context` pmcp ever held for that
`(server, task_id)`: the current record's if it has one, else the
snapshot's. Rev 3 sent `(current or snapped).requestor_context`. A record
evicted mid-teardown and then re-tracked by a concurrent `tasks/list` or
`tasks/get` exists, so it won, and it has no context, because neither path
passes one to `_record_task`. A context-scoped downstream can then refuse
the cancel. That would bring back round 1's failure (the refusal raises out
of the teardown) or round 2's (the run keeps going).

*Rev 4's audit was one step short (round-4 F001).* It classified every read
of a stored context and concluded that only the teardown held one across an
await. That was false:
- `get_task`, `get_task_result` and `_send_task_cancel` each read the stored
  context before their await, but recorded the reply *without* it.
- If the cap evicted the record during that await, the re-recorded task had
  no context.
- Every later cancel of it then went out without one, whether from a forced
  teardown or from `gateway.tasks_cancel` called with no context.

The seat's falsifier sent `{'taskId': 't', 'force': True}` on rev 4; main
sends the context. Fixing these three sites as well would have been the
fourth patch to this class in four rounds.

**Rev 5 removes the degree of freedom at the choke point.**
- **`_record_task(..., *, requestor_context)` is required, keyword-only, and
  has no default.** Every caller must pass the context it holds for the
  task, or a `None` it can justify. Its merge is unchanged: what the caller
  passes, else the existing record's.
- **One function, `_record_reply`, records a reply received after an
  await.** It takes the context pmcp held before the await, `stored_context`,
  as a required keyword. It writes that context back *unless the reply
  names a different task*; in that case the context is not that task's.
- **The functions that lead to `_record_reply` take the held context as a
  required keyword too.** They are `_fetch_task` (split out of `get_task`, so
  that `get_task_result`'s fallback hands on the context it read rather than
  re-reading a possibly evicted record) and `_send_task_cancel`.

So "held across an await" no longer matters for context: whatever a
function held is always written back.

`test_every_record_write_passes_the_context_its_caller_held` makes this
structural:
- It inspects the four signatures: keyword-only, no default.
- It collects every call to the four functions in `src/pmcp` from the AST,
  as `(callee, caller, value)`, and compares that set whole against
  `CONTEXT_FLOW`. That table has 10 entries, each with its reason.
- The two `None`-shaped entries are justified:
  - `list_tasks`: a listing does not attribute a context to a task. A
    tracked task keeps its own through the merge; an evicted one had already
    lost it, which is the stated residual.
  - `_record_reply`'s other-task branch.
- `cancel_task` passes the tracked record's context, not the caller's
  override, as main kept it.

Every path that records a reply after an await has a falsifier, in
`test_a_reply_recorded_after_an_eviction_keeps_the_held_context`:
`tasks/get`, `tasks/result`, the `tasks/result` → `tasks/get` fallback,
`tasks/cancel`, and the teardown cancel. In each, `t` is evicted during the
first request's await. The test asserts that the reply's record keeps the
context, and that the next cancel sends it. All five fail on rev 4's
manager, measured, and so does the seat's falsifier as written,
`test_get_task_keeps_the_context_it_held_if_evicted_mid_call`.
`test_a_reply_naming_another_task_does_not_take_this_tasks_context` pins the
other-task guard.

The mutants are M42a–M42g, one per caller, each dropping its held context to
`None`; M42h, which removes the other-task guard; M42i, where
`_record_reply` writes nothing; and M43, which gives `requestor_context` its
default back.

`test_every_read_of_a_stored_context_is_classified` (rev 4) stays, with
the same five reads.

*Why not in `put` (rev 4's argument, still true).* `put` stores whole
records built by `_record_task`, the one builder. After an eviction, nothing
the registry can see holds the context, so a merge in `put` could not
recover it. The callers hold it; rev 5 makes them hand it over.

**The "no connection that supports tasks" rule (rev 4; worded exactly in
rev 5).** A snapshot task whose server cannot be sent a task request at
that moment is skipped. No `tasks/cancel` is sent, the helper does not count
it, and it is not an error. That covers three cases:
- a concurrent disconnect removed the client;
- a reconnect has the client listed but not yet connected;
- the server no longer advertises tasks.

This applies whether the task is still tracked or was evicted. The check is
`_task_client_unavailable`, the same predicate `_task_client` raises on, so
the two cannot drift. Rev 3 skipped only a removed server. A reconnecting
one raised "not connected" out of the forced teardown, and
`handlers.disconnect_server` has no `try`.

*Why skip, not fail.* A forced teardown that fails on a task it cannot reach
is F001's shape again. A retry cannot succeed while the reconnect is in
progress either. For a tracked task the record stays, so `gateway.tasks_get`
and `gateway.tasks_cancel` reach it once connected. Main differs: for a
tracked record, `cancel_task` raised. The CHANGELOG states the residual: on
a remote server that is reconnecting, such a task is not cancelled.

Pinned by `test_a_teardown_skips_a_task_whose_server_has_no_live_connection`
(removed, reconnecting, tracked-reconnecting), and by mutants M28b (no skip)
and M39 (rev 3's narrower rule).

*`cancelled_task_count` (rev 5, round-4 non-blocking): worded, not
changed.* `gateway.disconnect_server` and `gateway.restart_server` report
`cancelled_task_count` as the active tasks that are no longer tracked after
the call, before minus after, as on main. A skipped task is therefore
included, though no cancel was sent for it. Reporting the helper's own count
instead would change the return types of `ClientManager.disconnect_server`
and `restart_server`, which are 3-tuples. Six test doubles implement them
(`test_tools`, `test_fresh_operator_baseline`, `test_package_identity_gate`,
`test_trust_boundaries_e2e`, `test_trust_boundaries_composition`,
`test_pkgid_panel_fixes`), and the handlers consume them. That is an
interface change beyond #338. The CHANGELOG now states the field's meaning
exactly. A follow-up issue can carry the interface change if the maintainer
wants it.

**Rev 3 and rev 4 reproduce main's outcome on both triggers:** `(True, 0, None)`,
`(2, [])`, and `tasks/cancel` sent for `['a', 'b']`, with `b`'s stored
context (*The F001 repro*). Rev 2's reasons against this do not hold:
- **"A second sender."** There is still exactly one: `cancel_task` and the
  helper share `_send_task_cancel`. Only the record check, which is the
  user-facing answer, stays in `cancel_task`.
- **"Nothing changes for a disconnect."** That is false for a remote server.
- **"Design decision 5."** That row concerns a task evicted *before* a
  teardown, which no snapshot holds. It is now stated exactly, and stays a
  residual (below).

**The residual that remains, stated exactly.** It is a task evicted *before*
a forced teardown starts. pmcp no longer tracks it, so no snapshot holds it,
and the teardown cannot cancel it. A stdio server's task ends when pmcp
terminates the process. **A remote server's task keeps running** after the
disconnect. `f001.py`'s `evicted-before` row shows it: with a cap of 1,
rev 3 sends `tasks/cancel` for `['a']` and main for `['a', 'b']`.

This is the price of any bound: pmcp cannot cancel what it no longer
remembers, and remembering it is the unbounded structure #338 removes. A
bounded tombstone list would just move the cap. The CHANGELOG, README and
SECURITY all name it, and all give the remedy: `gateway.tasks_get`, then
`gateway.tasks_cancel`.

**The refresh corollary (verified).** The loop at `handlers.py:2107` (rev 2
numbering) called `disconnect_server(name, force=True)` and dropped the
result. Measured on main with `refresh_ignored.py`:
- a forced disconnect that returns `(False, 0, "Error closing transport")`,
  the transport-close failure path main already has;
- gave `refresh ok: True errors: None`;
- with the server still in `_clients`.

The server is one that refresh decided to remove: it was deleted from the
config, denied by policy, or its config changed. **Decided: report it, and
keep going.** Each failure appends `Server '<name>' could not be
disconnected: <reason>` to `errors`, so `ok` is false. The other servers are
still disconnected and connected; one stuck server does not abort the rest.
The reason text is what `gateway.disconnect_server` already returns to the
same caller, so nothing new is exposed. Rev 2 measures
`refresh ok: False errors: ["Server 'gone' could not be disconnected: Error
closing transport"]` (mutants M30 and M31).

### 10. `TaskRegistry` keys (rev 2, N3)

`__getitem__` raises `KeyError` for anything that is not a 2-tuple. That
covers a string: `"st"` would otherwise unpack to `("s", "t")` and *find* a
record. It also raises `KeyError` for a tuple with an unhashable part. So
`get` and `in` keep the `Mapping` contract: `None` and `False`, never
`ValueError` or `TypeError` (`test_a_key_that_is_not_a_pair_is_absent_not_an_error`,
six keys; mutants M32 and M33).

### 11. Task state is bound to the connection it came from (rev 5, codex F001)

**The finding.** `_cancel_tracked_for_teardown` checked availability by
server *name*. While an earlier cancel awaited, a reconnect could:
- clean up `beta`, dropping its records;
- register a replacement client for `beta`, possibly another URL or tenant.

**The class.** Every outbound task request that pmcp derives from stored
state, a task id or a context, must go to the connection that state came
from. Every record pmcp keeps must come from the server's *current*
connection.

**One mechanism, enforced at the funnel.**
- **`ManagedClient.connection_id`** is unique for the process lifetime,
  taken from an `itertools.count`. `id()` is not used, because a later
  object can reuse it. A reconnect makes a new `ManagedClient`, so the new
  connection gets a new id.
- **`McpTaskRecord._connection_id`** (private) is stamped by
  `_record_task(..., connection=)`. That parameter is keyword-only and
  required. If `connection` is no longer `self._clients[server]`, the record
  is built and returned but **not stored**: a reply from the old connection
  must not become state of the new one. `None` (an unbound record) exists
  for tests that seed the registry; every call in `src/pmcp` passes the
  connection it sent on.
- **`_task_client(server, *, bound_to)`** is the only way to get a
  connection for a `tasks/*` request. `bound_to` is keyword-only and
  required. Through `_task_client_unavailable`, it refuses a record whose
  `_connection_id` differs from the server's current connection, with
  `Server <name> was reconnected; this task belongs to its previous
  connection`.
- **The teardown checks the snapshot entry's binding first,**
  `_task_client_unavailable(server, bound_to=snapped)`, before the terminal
  check and before the send. A mismatch is "server gone": skipped, not
  counted, not an error. It sends with `bound_to=snapped`.

**Every send site, derived from the AST.**
`test_every_task_request_is_bound_to_the_connection_its_state_came_from`
finds every `_send_request(…, "tasks/…")` in `src/pmcp`. Each must get its
connection from exactly one `_task_client(…, bound_to=…)` call in the same
function. `TASK_SENDS` lists the four:
- `list_tasks` → `tasks/list`, with `None`: a listing is the caller's
  query, built from no stored state. Its cursor comes from the caller.
- `_fetch_task` → `tasks/get`, with `bound_to`.
- `get_task_result` → `tasks/result`, with `record`.
- `_send_task_cancel` → `tasks/cancel`, with `bound_to`.

The test also collects every call that passes a binding on (`bound_to=` or
`connection=`) and compares them, as `(callee, caller, value)`, with the 12
entries in `BINDINGS`. It inspects the six binding parameters: keyword-only,
no default. `tools/call` is not a `tasks/*` send. It creates the task and
records it with `connection=managed`, the connection it called.

**Replacement paths drop the old records.**
`test_every_connection_replacement_drops_the_names_records_first` finds
every function that registers a connection (`self._clients[...] = ...`).
There are three: `_connect_stdio`, `_connect_remote_stream` and
`adopt_process`. Each must call `_cleanup_client` or `_remove_server_indexes`
earlier in its body. That covers records that existed at the replacement.
The `_record_task` check covers a reply that arrives afterwards, and the
`_task_client` binding covers a snapshot or record held across it.
Mutant M56 removes the drop on the stdio path, and the test catches it.

**What the caller sees.**
- For a record from a previous connection, `gateway.tasks_get`,
  `tasks_result` and `tasks_cancel` fail with the "was reconnected"
  message. They do not send on the new connection. In practice this needs
  a record that outlived its connection, which the drop above prevents;
  the check is the backstop.
- A reply that arrives after its connection was replaced is not recorded,
  so `gateway.invoke` would no longer see a record. Its default redaction
  was "the record exists", so it now also redacts any reply that carries a
  task id. `test_invoke_redacts_a_task_reply_by_default_even_when_not_recorded`
  pins this, and mutant M55 removes it.

**Tests.**
- codex's falsifier, as written, with rev 5's required keywords added:
  `test_teardown_does_not_send_old_context_to_a_replacement_server`;
- the three bound sends refused: `get`, `result` and `cancel`;
- the teardown skipping an entry from a previous connection;
- the five record paths, each with its connection replaced in flight
  (`tools/call`, `tasks/list`, `tasks/get`, `tasks/result`, `tasks/cancel`):
  the reply is not recorded;
- the invoke redaction case;
- the two structural tests.

**Mutants M46–M56** cover:
- storing a replaced connection's reply;
- the funnel ignoring the binding;
- the teardown checking only the server, or sending unbound;
- `get_task_result`, `get_task` or `cancel_task` sending unbound;

## Documentation impact

### The three #337 CHANGELOG corrections, each checked against the code

1. **"A `NaN` inside a tool result now reaches the caller as a `NaN` token."**
   The issue says this applies to every relayed downstream value. I
   measured it on the spike (`nan_relay.py`, reproduced
   below). The script uses the real `ClientManager` and `GatewayTools`, puts
   a `NaN` in each reply, and serialises the output with the gateway's own
   encoder, `json.dumps(result.model_dump(), indent=2)`
   (`server.py:450-467`):

   | Gateway tool | Where the NaN was | `NaN` token in the caller's output |
   |---|---|---|
   | `gateway.invoke` | tool result | **yes** |
   | `gateway.tasks_result` | `result` | **yes** |
   | `gateway.tasks_get` | task `raw` | no (`raw` is nulled, as #337's entry says) |
   | `gateway.tasks_list` | task `raw` | no |

   Resource reads (`server.py:618-630`) and prompt gets (`:688-702`) pass on
   only `uri`, `mimeType` and `text` strings, so no number from the
   downstream reaches the caller there.

   So "not just tool results" is right, but "every relayed value" is too
   broad. The corrected text names both paths that relay a value as sent,
   and the two that do not.
2. **"a string where a number is expected"**. Measured with
   `_task_info_from_payload`:
   - `ttl: "5"` and `pollInterval: "5"` are unusable;
   - `createdAt: "5"`, `createdAt: "2026-01-02T03:04:05Z"`,
     `lastUpdatedAt: "5.5"` and the same ISO string are **kept**: 5.0,
     1767323045.0, 5.5 and 1767323045.0;
   - `lastUpdatedAt: "soon"` is unusable.

   The source is `_usable_task_timestamp` (`types.py:563-596`): "a numeric
   string or an ISO 8601 string". The bullet becomes: a string for `ttl` or
   `pollInterval` (a numeric or ISO 8601 string is still accepted for
   `createdAt` and `lastUpdatedAt`/`updatedAt`).
3. **"now reports `updatedAt: null`"**. `McpTaskInfo` declares `updated_at`
   and no alias (`types.py:633`). A recorded task with an unusable
   `lastUpdatedAt` dumps the key `updated_at` with value `None`, and `raw`
   keeps the wire key `lastUpdatedAt` (measured). The text becomes
   `updated_at: null`.

## Non-goals

- **Making the caps configurable.** Main had a constant; nobody has asked.
- **Forwarding `tasks_cancel` for an unknown id**, or keeping tombstones of
  evicted ids (Design decision 5).
- **Bounding the size of one `tasks/list` reply.** The cap bounds what pmcp
  *tracks*. A listing is returned whole, and its page size is the
  downstream's. pmcp's response-size limits apply to it as to any reply.
- **NaN in relayed results.** That is Consiliency/pmcp#335. Only the wording
  of #337's entry is corrected here.
- **Time-based expiry (`ttl`).** pmcp does not expire records by the
  downstream's `ttl`; the units question is Consiliency/pmcp#330.

## Unverified

- **Memory at the total.** 1000 records, each holding a downstream `raw`
  dict, are bounded in count, not in bytes. A downstream can still send a
  large `raw`. That is the same exposure as on main, now capped at 1000
  instead of unbounded.
- **Real downstream servers.** All paths were driven with a canned
  `_send_request` through the real manager code and handlers, and with no
  live MCP server. #337's transport tests cover the wire.

````python
"""The registry of downstream MCP tasks pmcp tracks (Consiliency/pmcp#338).

`TaskRegistry.put` is the only way a record gets in, and it applies both caps
before it returns, so no record path can skip them:

- **Per server:** at most `per_server` records for one server, finished and
  unfinished alike. Past it, that server's own records are evicted, so one
  downstream cannot push out another's.
- **Total:** at most `total` records across all servers, as a backstop for a
  gateway with many servers. Past it, the evicted record comes from the server
  holding the most records.

Victim order, inside the chosen server:

1. Finished records (`completed`, `failed`, `cancelled`) go before unfinished
   ones. A finished record only caches a final status the downstream still
   serves. An unfinished one is what `tasks_cancel`, the disconnect refusal and
   the stored `requestor_context` depend on.
2. Within each class, the record pmcp recorded least recently goes first. This
   is pmcp's own sequence, which no downstream clock can move
   (Consiliency/pmcp#298).

The record `put` just stored is never evicted by that same `put`. The caller
reads it straight back, for example for `gateway.invoke`'s default redaction.

The mapping is read-only: no `__setitem__`, `pop` or `update`. Writes go
through `put`; removals go through `drop_server` (a disconnect) and `clear`
(shutdown).
"""

from __future__ import annotations

from collections.abc import Iterator, Mapping

from pmcp.types import McpTaskRecord

#: Statuses after which a downstream task cannot change again.
TERMINAL_TASK_STATUSES = frozenset({"completed", "failed", "cancelled"})

#: Default per-server cap. This was the old shared cap on finished records; it
#: now applies to each server, counting finished and unfinished records.
DEFAULT_TASKS_PER_SERVER = 100

#: Default total cap: ten servers at their per-server cap.
DEFAULT_TASKS_TOTAL = 1000

TaskKey = tuple[str, str]


def task_is_terminal(record: McpTaskRecord) -> bool:
    return record.status in TERMINAL_TASK_STATUSES


class TaskRegistry(Mapping[TaskKey, McpTaskRecord]):
    """Records keyed by `(server_name, task_id)`, with a cap per server and a
    total cap, both enforced in `put`."""

    def __init__(
        self,
        *,
        per_server: int = DEFAULT_TASKS_PER_SERVER,
        total: int = DEFAULT_TASKS_TOTAL,
    ) -> None:
        if per_server < 1 or total < 1:
            raise ValueError("task caps must be at least 1")
        self.per_server = per_server
        self.total = total
        # server -> task_id -> record. Each inner dict is kept in record order:
        # `put` removes a key before inserting it again, so iterating a bucket
        # yields its least recently recorded task first.
        self._by_server: dict[str, dict[str, McpTaskRecord]] = {}
        self._count = 0
        self._order = 0

    # -- read-only Mapping ----------------------------------------------------

    def __getitem__(self, key: TaskKey) -> McpTaskRecord:
        # Anything that is not a `(server, task_id)` tuple is simply absent:
        # `KeyError`, which `Mapping.get` and `in` turn into None and False.
        # (Unpacking alone would read the string "st" as ("s", "t").)
        if not (isinstance(key, tuple) and len(key) == 2):
            raise KeyError(key)
        server_name, task_id = key
        try:
            return self._by_server[server_name][task_id]
        except TypeError:  # an unhashable part
            raise KeyError(key) from None

    def __iter__(self) -> Iterator[TaskKey]:
        for server_name, bucket in self._by_server.items():
            for task_id in bucket:
                yield (server_name, task_id)

    def __len__(self) -> int:
        return self._count

    # -- writes ---------------------------------------------------------------

    def put(self, record: McpTaskRecord) -> list[McpTaskRecord]:
        """Store `record` as the most recently recorded task, then apply both
        caps. Returns the records evicted, in the order they went."""
        bucket = self._by_server.setdefault(record.server_name, {})
        if bucket.pop(record.task_id, None) is None:
            self._count += 1
        self._order += 1
        record._recorded_order = self._order
        bucket[record.task_id] = record

        new_key = (record.server_name, record.task_id)
        evicted: list[McpTaskRecord] = []
        while len(bucket) > self.per_server:
            evicted.append(self._evict(record.server_name, new_key))
        while self._count > self.total:
            evicted.append(self._evict(self._largest_server(new_key), new_key))
        return evicted

    def drop_server(self, server_name: str) -> None:
        """Forget every record of one server (it disconnected)."""
        bucket = self._by_server.pop(server_name, None)
        if bucket:
            self._count -= len(bucket)

    def clear(self) -> None:
        self._by_server.clear()
        self._count = 0

    # -- eviction ---------------------------------------------------------------

    def _candidate(self, server_name: str, new_key: TaskKey) -> McpTaskRecord | None:
        """The record `server_name` gives up next: its oldest finished record,
        else its oldest unfinished one. Never the record `put` just stored
        (`new_key`); None when that is all the server holds."""
        fallback: McpTaskRecord | None = None
        for task_id, record in self._by_server[server_name].items():
            if (server_name, task_id) == new_key:
                continue
            if task_is_terminal(record):
                return record
            if fallback is None:
                fallback = record
        return fallback

    def _largest_server(self, new_key: TaskKey) -> str:
        """The server the total cap takes from: the one holding the most
        records. On a tie, the one whose next victim was recorded first."""
        chosen: str | None = None
        chosen_rank: tuple[int, int] | None = None
        for server_name, bucket in self._by_server.items():
            victim = self._candidate(server_name, new_key)
            if victim is None:
                continue
            rank = (len(bucket), -victim._recorded_order)
            if chosen_rank is None or rank > chosen_rank:
                chosen, chosen_rank = server_name, rank
        assert chosen is not None, "over the total cap, another record exists"
        return chosen

    def _evict(self, server_name: str, new_key: TaskKey) -> McpTaskRecord:
        victim = self._candidate(server_name, new_key)
        assert victim is not None, "a server over its cap holds another record"
        bucket = self._by_server[server_name]
        del bucket[victim.task_id]
        self._count -= 1
        if not bucket:
            del self._by_server[server_name]
        return victim
````

````python
def _reference_victim(
    log: list[tuple[str, str, bool]], server: str, new: tuple[str, str]
) -> tuple[str, str]:
    """Plain restatement of the rule, over a list kept in record order."""
    mine = [e for e in log if e[0] == server and (e[0], e[1]) != new]
    finished = [e for e in mine if e[2]]
    victim = (finished or mine)[0]
    return (victim[0], victim[1])


def test_the_registry_matches_a_plain_restatement_of_the_rule() -> None:
    """Random puts (re-records, every status class, several servers, both caps
    binding) against a reference model written as list scans."""
    rng = random.Random(338)
    statuses = ["working", "completed", "failed", "cancelled", None, "input_required"]
    for per_server, total in ((3, 7), (5, 5), (4, 100), (100, 6), (1, 2)):
        registry = TaskRegistry(per_server=per_server, total=total)
        log: list[tuple[str, str, bool]] = []  # (server, task_id, finished)
        for _ in range(600):
            server = rng.choice("abcd")
            task_id = str(rng.randrange(12))
            status = rng.choice(statuses)
            record = McpTaskRecord(server_name=server, task_id=task_id, status=status)
            new = (server, task_id)
            log = [e for e in log if (e[0], e[1]) != new]
            log.append((server, task_id, task_is_terminal(record)))
            expected: list[tuple[str, str]] = []
            while sum(1 for e in log if e[0] == server) > per_server:
                victim = _reference_victim(log, server, new)
                expected.append(victim)
                log = [e for e in log if (e[0], e[1]) != victim]
            while len(log) > total:
                # the server holding the most; on a tie, the oldest victim
                # (`log` is in record order, so its index is the age)
                ranked = []
                for s in {e[0] for e in log}:
                    if any(e[0] == s and (e[0], e[1]) != new for e in log):
                        v = _reference_victim(log, s, new)
                        index = [(e[0], e[1]) for e in log].index(v)
                        size = sum(1 for e in log if e[0] == s)
                        ranked.append(((size, -index), v))
                victim = max(ranked)[1]
                expected.append(victim)
                log = [e for e in log if (e[0], e[1]) != victim]
            evicted = registry.put(record)
            assert [(r.server_name, r.task_id) for r in evicted] == expected
            assert sorted(registry) == sorted((e[0], e[1]) for e in log)
            assert registry[new] is record
            assert len(registry) == len(log) <= total

# --- structure: one way in ---------------------------------------------------------------


def _functions(tree: ast.AST) -> list[ast.FunctionDef | ast.AsyncFunctionDef]:
    return [
        n
        for n in ast.walk(tree)
        if isinstance(n, ast.FunctionDef | ast.AsyncFunctionDef)
    ]


def _calls(func: ast.AST, attr: str) -> bool:
    return any(
        isinstance(n, ast.Call)
        and (
            (isinstance(n.func, ast.Attribute) and n.func.attr == attr)
            or (isinstance(n.func, ast.Name) and n.func.id == attr)
        )
        for n in ast.walk(func)
    )


def _where(attr: str) -> set[tuple[str, str]]:
    found = set()
    for path in SRC.rglob("*.py"):
        tree = ast.parse(path.read_text())
        for func in _functions(tree):
            # innermost function only: skip one whose nested function calls it
            inner = [f for f in _functions(func) if f is not func]
            if _calls(func, attr) and not any(_calls(f, attr) for f in inner):
                found.add((str(path.relative_to(SRC)), func.name))
    return found

def _owned(
    attr_test: Callable[[ast.AST, ast.AST | None], str | None],
) -> set[tuple[str, str, str]]:
    """(file, innermost function, label) for every node in src/pmcp for which
    `attr_test(node, parent)` returns a label."""
    found = set()
    for path in SRC.rglob("*.py"):
        tree = ast.parse(path.read_text())
        parents = {c: n for n in ast.walk(tree) for c in ast.iter_child_nodes(n)}
        for node in ast.walk(tree):
            label = attr_test(node, parents.get(node))
            if label is None:
                continue
            owner: ast.AST | None = node
            while owner is not None and not isinstance(
                owner, ast.FunctionDef | ast.AsyncFunctionDef
            ):
                owner = parents.get(owner)
            name = owner.name if owner is not None else "<module>"
            found.add((str(path.relative_to(SRC)), name, label))
    return found

# --- snapshot-then-await sites (rev 2, panel finding F001) -------------------------
#
# A site that reads tracked records and then awaits can find a record gone when
# it resumes: the cap evicted it (another caller recorded a task on that server,
# or the downstream answered `tasks/cancel` with a different task id), or a
# disconnect dropped it. Each site has a defined outcome for that, pinned below.
# Records are made in the order b, a: the active-task snapshot is sorted by id
# (a, b), so cancelling `a` first and recording one more task evicts `b`, the
# oldest unfinished record, while it is still waiting its turn. `b` carries a
# stored requestor_context, which its cancel must still send (rev 3: an
# evicted task is cancelled by its snapshot, not skipped).

B_CONTEXT = {"tenant": "t-b"}


def _teardown_manager(
    trigger: str,
) -> tuple[ClientManager, dict[tuple[str, str], Any], list[tuple[str, Any]]]:
    manager, replies = _manager("tasks")
    manager._tasks.per_server = 2
    manager._tasks.put(
        McpTaskRecord(
            server_name="tasks",
            task_id="b",
            status="working",
            requestor_context=B_CONTEXT,
        )
    )
    _put(manager._tasks, "tasks", "a", "working")
    sent: list[tuple[str, Any]] = []
    plain = manager._send_request

    async def send(managed: ManagedClient, method: str, params: Any, **kw: Any) -> Any:
        sent.append((method, params))
        if method == "tasks/cancel":
            task_id = params["taskId"]
            if trigger == "concurrent-record":
                # another caller's tasks_list lands while this cancel is in flight
                replies[("tasks", "tasks/list")] = {
                    "tasks": [{"taskId": f"new-{task_id}", "status": "working"}]
                }
                await asyncio.gather(manager.list_tasks("tasks"))
                return {"taskId": task_id, "status": "cancelled"}
            if trigger == "re-tracked-without-context":
                # rev 4 (round-3 F001): a concurrent tasks_list lists a new
                # task (evicting b) and then b itself, which is recorded again
                # with no requestor_context
                if task_id == "a":
                    replies[("tasks", "tasks/list")] = {
                        "tasks": [
                            {"taskId": "x", "status": "working"},
                            {"taskId": "b", "status": "working"},
                        ]
                    }
                    await manager.list_tasks("tasks")
                    re_tracked = manager.get_task_record("tasks", "b")
                    assert re_tracked is not None
                    assert re_tracked.requestor_context is None
                return {"taskId": task_id, "status": "cancelled"}
            # the downstream answers with a different task id
            return {"taskId": f"other-{task_id}", "status": "working"}
        return await plain(managed, method, params, **kw)

    manager._send_request = send  # type: ignore[method-assign, assignment]
    return manager, replies, sent


TRIGGERS = ["concurrent-record", "foreign-task-id"]
#: For the sites that hold a context across an await (rev 4): also a record
#: evicted and then re-tracked, context-less, by a concurrent listing.
CONTEXT_TRIGGERS = [*TRIGGERS, "re-tracked-without-context"]


def _cancelled_ids(sent: list[tuple[str, Any]]) -> list[str]:
    return [params["taskId"] for method, params in sent if method == "tasks/cancel"]


def _b_cancel_carries_its_context(sent: list[tuple[str, Any]]) -> bool:
    return any(
        method == "tasks/cancel"
        and params["taskId"] == "b"
        and params["task"]["requestorContext"] == B_CONTEXT
        and params["force"] is True
        for method, params in sent
    )


@pytest.mark.parametrize("trigger", CONTEXT_TRIGGERS)
@pytest.mark.asyncio
async def test_forced_cancel_loop_survives_concurrent_records(trigger: str) -> None:
    """F001's falsifier, `ClientManager.disconnect_server(force=True)`: `b` is
    evicted while `a`'s cancel is in flight. On rev 1 the disconnect returned
    `(False, 0, 'Task not found: tasks::b')`; rev 2 skipped `b`. Like main,
    rev 3 returns `(True, 0, None)` and sends `tasks/cancel` for both: on a
    remote server, `b` would otherwise keep running after the disconnect."""
    manager, _replies, sent = _teardown_manager(trigger)
    result = await manager.disconnect_server("tasks", force=True)
    assert result == (True, 0, None), result
    assert _cancelled_ids(sent) == ["a", "b"]
    assert _b_cancel_carries_its_context(sent)
    assert "tasks" not in manager._clients and len(manager._tasks) == 0

_ACCESSORS = {"get_active_tasks", "get_tracked_tasks", "get_task_record"}


def _reads_records(n: ast.AST, readers: Collection[str] = ()) -> bool:
    """Any *reference* to a way of reading tracked records, not only a direct
    call (rev 3, N2): `x.get_active_tasks` as an attribute (called, aliased,
    or passed as a bound method), the bare name, `getattr(x,
    "get_active_tasks")`, and `_tasks` -- and (rev 4, N2b) any reference to
    one of `readers`, the sync helpers that read."""
    names = _ACCESSORS | {"_tasks"} | set(readers)
    return (
        (isinstance(n, ast.Attribute) and n.attr in names)
        or (isinstance(n, ast.Name) and n.id in names)
        or (isinstance(n, ast.Constant) and n.value in names)
    )


def _sync_readers(trees: list[ast.AST]) -> set[str]:
    """Names of the functions whose reads run *inline* in their caller --
    before the caller's next await -- closed to a fixpoint (rev 4, N2b;
    rev 5, N2c):
    - a plain `def` that reads, directly or through another inline reader;
    - an `async def` that reads and never awaits. Awaiting it runs its body to
      completion without suspending, exactly like calling a sync helper. The
      round-4 seat measured this dodge.

    An `async def` that suspends is not included: its reads are scanned in
    its own body as a site of its own. Following its *returned* value into
    every caller by name was measured and rejected: by name-matching it flags
    28 to 93 functions across `src/pmcp` (`refresh`, `call_tool`, `main`
    collide), which would make the table meaningless. `__init__` binds
    `_tasks`; it does not read it."""
    readers: set[str] = set()
    while True:
        found = {
            func.name
            for tree in trees
            for func in _functions(tree)
            if func.name != "__init__"
            and (
                isinstance(func, ast.FunctionDef)
                or not any(isinstance(n, ast.Await) for n in ast.walk(func))
            )
            and any(_reads_records(n, readers) for n in ast.walk(func))
        }
        if found <= readers:
            return readers
        readers |= found


def _snapshot_sites(tree: ast.AST, readers: set[str]) -> set[str]:
    """Functions that read tracked records -- directly, or through a call to
    one of `readers` -- before one of their awaits ends."""
    found = set()
    for func in _functions(tree):
        if func.name == "__init__":
            continue
        reads = [
            (n.lineno, n.col_offset)
            for n in ast.walk(func)
            if _reads_records(n, readers)
        ]
        # where each await *finishes*: a read inside an awaited expression's
        # arguments still happens before that await resumes
        awaits = [
            (n.end_lineno or n.lineno, n.end_col_offset or 0)
            for n in ast.walk(func)
            if isinstance(n, ast.Await)
        ]
        # in a loop, a read can come before the *next* iteration's await
        looped = any(
            any(_reads_records(n, readers) for n in ast.walk(loop))
            and any(isinstance(n, ast.Await) for n in ast.walk(loop))
            for loop in ast.walk(func)
            if isinstance(loop, ast.For | ast.AsyncFor | ast.While)
        )
        if reads and awaits and (min(reads) < max(awaits) or looped):
            found.add(func.name)
    return found


def test_every_snapshot_then_await_site_is_classified() -> None:
    """A function that reads tracked records (any reference to an accessor,
    or `_tasks`) and then awaits is a site where a record can vanish in
    between. Each one must be in SNAPSHOT_SITES, with its defined outcome and
    a test above."""
    trees = {path: ast.parse(path.read_text()) for path in SRC.rglob("*.py")}
    readers = _sync_readers(list(trees.values()))
    found = {
        f"{path.relative_to(SRC)}:{name}"
        for path, tree in trees.items()

    }
    assert found == set(SNAPSHOT_SITES)

def test_every_record_write_passes_the_context_its_caller_held() -> None:
    """Round-4 F001, fixed at the choke point rather than site by site: no
    call that leads to `_record_task` can leave the context out, and every
    value passed is listed with its reason."""
    import inspect

    for callee, parameter in _CONTEXT_PARAMETERS.items():
        signature = inspect.signature(getattr(ClientManager, callee))
        param = signature.parameters[parameter]
        assert param.kind is inspect.Parameter.KEYWORD_ONLY, callee
        assert param.default is inspect.Parameter.empty, callee

    found = set()
    for path in SRC.rglob("*.py"):
        tree = ast.parse(path.read_text())
        for func in _functions(tree):
            for node in ast.walk(func):
                if not (
                    isinstance(node, ast.Call)
                    and isinstance(node.func, ast.Attribute)
                    and node.func.attr in _CONTEXT_PARAMETERS
````

````python
    return ManagedClient(
        config=ResolvedServerConfig(name=name, source="custom",
            config=RemoteMcpServerConfig(type="streamable-http", url=url)),
        is_remote=True, write_stream=object(),
        status=ServerStatus(name=name, status=ServerStatusEnum.ONLINE, tool_count=0,

    replacement = client("beta", "https://new-tenant.example/mcp")

    def rec(server: str, task: str, ctx: Any, conn: ManagedClient) -> None:
        kw: dict[str, Any] = {"requestor_context": ctx}
        if "connection" in params:
````
