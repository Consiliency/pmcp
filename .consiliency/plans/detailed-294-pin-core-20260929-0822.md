## Goal

An operator can hold a shipped (or overlay) npx-launched MCP client at one exact version with
one line:

```yaml
# ~/.pmcp/manifest.yaml (or an approved project overlay)
server_version:
  firecrawl: "3.25.5"
```

or `version: "3.25.5"` on a whole `servers:` entry. After that:
- **Every argv that spawns the server** runs `firecrawl-mcp@3.25.5`: `args` (what
  `client/manager.py` spawns) and **every** platform's `install` argv (what
  `gateway.provision` → `start_install` runs and adopts).
- **`gateway.update_server`** refuses to move the server (main's existing refusal, unchanged),
  and now also returns `pinned_version="3.25.5"`.
- **`pmcp update`** prints `[PINNED] firecrawl: pinned at 3.25.5` instead of `[FAILED] …`.

## Design

**D1. Where a pin comes from.**
- `version:` on a `servers:` entry, in the shipped manifest or an overlay; or
- `server_version: {<name>: <version>}` in an overlay (user overlay, approved project
  overlay, `PMCP_MANIFEST_PATH`). It patches an existing entry, like `server_env:`: applied
  after that source's `servers:` replaces, and never creating a server.

Sources apply in main's overlay order (shipped, user, project). A later source's
`server_version` pin wins, and a later whole-entry replace drops an earlier pin. Pins are
materialised **once, after every source**, so the pin written into argv is the final one.
An unapproved project overlay contributes nothing (main's consent gate, unchanged).

**D2. What a pin may be.** Exactly one version by main's own npm-aware grammar,
`validation.is_valid_package_version`, which the provision gate already requires of an argv
pin. It must be a YAML **string**, with no `+` build metadata.

Everything else is refused, and the entry is left unchanged: a range (`^3.25.5`, `3.x`, `*`),
a dist-tag (`latest`), a `v` prefix, a YAML number, an empty string, a package spec
(`evil-pkg@1.0.0`, `npm:…`), a path, whitespace or a flag, and a SemVer-shaped tarball name
(`3.25.5-corp.tgz`, which npa reads as a file). The value never names the package: the name
is always the entry's own.

**D3. Where it is written: the npx package slot, and only a plain same-name registry spec.**
The slot is the provision gate's: the first argument after the allowlisted leading npx flags
(`provision_gate._NPX_LEADING_FLAGS`). `split_plain_registry_spec` accepts only three
spellings:
- `name`: npa reads it as the registry range `*`;
- `name@<exact version>`: npa `version`;
- `name@<dist-tag>`: npa `tag`.

It refuses, by npa class: alias, URL, git, hosted git, file, directory, every range, a
tarball name or selector (checked **before** "is it a version", as npa does), a tag word npa
reads as a version or range (`x`, `v1`, `vvX`), and the names npm excludes (`node_modules`,
`favicon.ico`). Only the version suffix is replaced; the name is kept. So a pin selects a
version of the package the entry already runs, and never another package:
`myalias@npm:x@1` would otherwise become the registry package `myalias`, and
`x@corp.TGZ` would turn a local tarball into a registry fetch.

**D4. All or nothing.** `args` and every non-empty `install` argv must be npx argvs whose slot
is a plain registry spec of the **same** package. Otherwise the pin is refused and the entry
is returned unchanged with `version=None`: pinning `args` but not `install` would approve X and
then run latest. The pin is also refused for:
- a remote server (no local client);
- a non-npx command (uvx, pip, cargo, docker): the log names the escape hatch, "pin it with
  explicit command and args in `.mcp.json` or `.pmcp.json`".

Materialisation is contained per entry. A malformed overlay entry (a non-string argv element)
costs only its own pin, never the manifest.

**D7. The entry's env must not be able to redirect npm.** The argv pin holds only if nothing the
**entry** puts in the child's environment can make npm run something else. This was measured on
real npm 10 and 11 (appendix):
- with the entry's `npm_config_package=alternate@9.0.0`, the materialised
  `npx -y pkg@1.2.3` runs **`alternate@9.0.0`**;
- with `npm_config_package=evil@1.0.0` (either case), it runs the pinned spec as a shell
  command;
- with `npm_config_registry`, it fetches from another registry.

So `_materialize_version_pin` refuses the pin, leaving the entry unchanged, when any key the
entry supplies is not **proven inert**. The keys checked are `extra_env` (which also carries
every overlay's `server_env` patch, applied before materialisation) and the `env_var`
credential key. The allowlist is rev 22's rule on Consiliency/pmcp#295, narrowed:
- the keys pmcp's **shipped** manifest declares for that server (`env_var`,
  `api_key_optional_when`), read from the packaged file directly, so an overlay cannot
  declare a key inert;
- locale and terminal keys (`LANG`, `LANGUAGE`, `LC_*`, `TERM`, `TZ`, `NO_COLOR`,
  `FORCE_COLOR`);
- npm's logging and timing config keys, read the way npm reads `npm_config_*` in any case:
  `loglevel`, `color`, `progress`, `timing`, `unicode`, `logs-dir`, `logs-max`, `fund`,
  `audit`, `update-notifier`, `yes`, the `fetch-retry*`/`fetch-timeout` family,
  `maxsockets`.

Everything else refuses, **including an empty value**: `npm_config_package`,
`npm_config_registry`, `npm_config_cache`, a `//registry/:_authToken`, `NODE_OPTIONS`,
`NODE_PATH`, `PATH`, `HOME`, `PREFIX`, `XDG_*`, `nvm_*`, a proxy, an unknown key.

A manifest entry cannot set a cwd. A config that runs the materialised argv (for example, a
`.pmcp.json` entry with no command) brings its own env and cwd, so `[PINNED]` (D6) is withheld
when that env fails the same rule or the config sets a cwd: a project's `.npmrc`, or a
`node_modules/<pkg>` whose `package.json` claims the pinned version, decides what npm runs
there.

**Trust boundary, stated.** The **host's** environment and npm configuration are trusted: the
shell that started pmcp, global and user `.npmrc`, npm's cache, and the working directory the
server inherits from pmcp, including a `node_modules` there. A pin fixes the npm spec (name and
exact version), and npm resolves it in that trusted environment. The rules above cover only
what an entry or overlay controls.

The cost: an overlay-only server with a credential (`env_var`) or any non-inert `extra_env`
key cannot be pinned this way. Pin it in its own `.mcp.json`/`.pmcp.json` args. Every shipped
server that can be pinned today still can (below).

**D5. Refusal logs are fixed text.** A refused pin logs one WARNING made of three parts:
- fixed text for the reason **category**;
- the field (`version` or `server_version`, a closed pair);
- the server, named **only if pmcp's shipped manifest defines that name**, read from the
  packaged file (`_server_label`). Any other name is an overlay's own key, which could be
  anything an operator pasted (a token), so it is shown as "an overlay server (name not
  shown)". No grammar decides what to show: revision 1's grammar admitted both
  credential shapes (round 1).

The pin value, an argv, a command, a package, a selector and an exception message are
**never** logged; only an exception's type name is.

A value refusal says "this pin is ignored; a pin from an earlier source, if any, stands". It
does not say "stays unpinned", because an earlier source's pin may hold (round 1, N2).
`server_version: {name: null}` means "no pin from this source". It neither pins nor unpins and
logs nothing; only removing the earlier line, or a whole-entry replace, takes a pin away.

**D6. `update_server` and `pmcp update`.** Main's reporting is unchanged, with one exception.
When main's own pin reader (`_detect_effective_version_pin`) finds a pin, `update_server` also
fills `pinned_version`, but only when all of these hold:
- the server's manifest entry carries a **materialised** pin (`version` set);
- the config being updated runs **exactly** the materialised argv (`[command, *args]` equal:
  a manifest-sourced config, or one that inherits the manifest's command and args);
- that config sets no cwd, and its env passes D7's rule;
- main's reader names the same version.

Main already re-reads the manifest on every `update_server` (`_resolve_lifecycle_target`), so
its refusal warnings already repeat per update. `_materialised_pin` adds one more read, only
when main's reader has found a pin (round 1, N4).

`pmcp update` prints `[PINNED] <server>: pinned at <version>` for such a result. Every other
result prints main's `[OK]`/`[FAILED] <server>: <message>` line, unchanged. The shown value is
a validated exact version the operator wrote, and the same string npx fetches. No registry
lookup, warning, judge or spawn-set is added.

**Shipped cost.** Of 107 shipped entries, 77 can be pinned (npx with a plain slot in `args`
and every `install`, and no shipped `extra_env` key D7 refuses), and 30 are refused: 19 uvx,
9 remote or empty-command, `cloudflare`, and `context7`, whose Windows install is
`cmd /c npx`. D7 refuses none of the shipped entries. As shipped (no pin), nothing changes.

## Acceptance criteria

- [ ] `server_version: {firecrawl: "3.25.5"}` makes `args == ["-y", "firecrawl-mcp@3.25.5"]`
  and every `install` argv `["npx", "-y", "firecrawl-mcp@3.25.5"]`, and the provision gate's
  `_config_runs_exactly(entry, "firecrawl-mcp@3.25.5")` is true.
- [ ] Every refused value and slot leaves `args`/`install` byte-identical, with
  `version is None`, and one fixed-text WARNING (naming the server only if pmcp ships it).
- [ ] No pin value, argv, command, package or exception text appears in a pin log; both
  sentinel shapes, in the property test.
- [ ] `update_server` on a materialised pin returns `pinned_version`; `pmcp update` prints
  `[PINNED] <server>: pinned at <v>`; every other result is reported as on main.
- [ ] A pin is refused (entry unchanged) when the entry's env has a key not proven inert

+def _parse_version_pin(name: str, raw: Any, field_label: str) -> str | None:
+    """Parse a client version pin, fail-soft and fail-closed.

+    provision gate already requires of an argv pin) or nothing. Refused, with

+    both re-resolve at every ``npx -y`` spawn, which is the drift a pin exists

+def split_plain_registry_spec(arg: str) -> tuple[str, str | None] | None:
+    """``(name, selector)`` if npm would fetch *arg* from the registry as
+    ``name`` at an exact version or a dist-tag; else ``None``.
+
+    Accepted: ``name`` (npa: registry range ``*``), ``name@<exact SemVer>``
+    (npa: ``version``) and ``name@<dist-tag>`` (npa: ``tag``). Refused, by
+    class: anything ``parse_package_spec`` rejects (URLs, aliases, git, paths,
+    flags: their name half is not a package name, or they have no name); an
+    unscoped name ending in a tarball suffix (npa: ``file``); a selector that
+    is not an exact version or a tag word (``:`` / ``/`` / ``~`` / ``.``-led
+    forms, i.e. alias, git, URL, file, directory, and every range); a tag word
+    ending in a tarball suffix (npa: ``file``); and a tag word that npm reads as
+    a version or range (``x``, ``v1``, ``vvX``); a SemVer-shaped selector that
+    ends in a tarball suffix (npa: ``file``, checked first); and the names
+    npm excludes (``node_modules``, ``favicon.ico``). Pure grammar: it never asks the
+    resolver, so it works while npm package identity is disabled.

+        return None

+    if selector is None:

+    # a SemVer-shaped tarball (`3.25.5-corp.tgz`) is a file, not a version.
+    if _NPM_FILE_TYPE_RE.search(selector):

+    if is_valid_package_version(selector):

+        selector

+    return None
