# Detailed plan: harden the HTTP auth surface — JWKS amplifier (S-07), JWKS fetch timeout (S-08), metadata Host reflection (S-10)

## Task
Fix the remainder of the 2026-09-01 codebase review finding tracked in Consiliency/pmcp#231: three defects on the HTTP auth surface (the gateway's trust boundary), where the dangerous direction is failing OPEN.

- **S-07** — unauthenticated outbound-fetch amplifier: an unknown `kid` forces an outbound JWKS refresh with no cooldown, and rate limiting runs *after* auth, so an unauthenticated caller drives repeated outbound fetches with random `kid`s.
- **S-08** — the JWKS fetch has no `ClientTimeout` and runs while holding `_refresh_lock`, so a slow/hanging JWKS endpoint stalls every request coroutine waiting on that lock (an async hang under the lock, not a synchronously blocked event loop). Worse, a *failed* refresh leaves no usable cache, so waiters acquire the lock in turn and each re-attempt the fetch — N concurrent callers time out sequentially and the last waits ~N×timeout.
- **S-10** — the OAuth protected-resource-metadata endpoint returns a Host-derived `resource` and its route never checks the Host allowlist, so a request with an attacker-supplied `Host` gets that Host advertised back as the resource.

S-09 is already fixed and merged in #281 — out of scope here.

## Research summary
All three findings were confirmed by reading the current tree at commit `af67207` (branch `plan/231-auth-surface`).

So the amplifier is reachable pre-rate-limit, unauthenticated.

## Design decisions (made explicitly)

### S-07 — global forced-refresh cooldown (not a per-kid negative cache, not reorder-before-auth)
**Decision:** add a per-`AsyncJWKS` cooldown that bounds *forced* refreshes to at most one per window (default 10 s). The cooldown is enforced **inside `get()`**, in two places that must both exist: a pre-lock fast path (an unexpired cache answers a forced refresh whenever `now - self._last_forced_refresh < self._forced_refresh_cooldown_seconds`, so callers on cooldown never queue on the lock) and the **authoritative re-check of the same condition under `_refresh_lock`**, immediately before the backoff gate and the stamp (round-4 finding; see "### S-07 concurrency" below for why the pre-lock check alone is a race). `get_for_token` carries no cooldown logic: it calls `get(force_refresh=True)` for any unknown `kid` and `get()` decides. During the cooldown an unknown `kid` returns the currently-cached JWKS (no outbound fetch). **The cooldown timestamp is advanced inside `get()`, only when a fetch is actually attempted (past the S-08 backoff gate) — on every attempted forced fetch, success or failure, and nowhere else.** Stamping a backoff-rejected attempt is the composition bug the round-3 review caught: see "### S-07 × S-08 composition" below. Stamping only on success is rejected deliberately: a failed fetch is still an outbound fetch the caller caused, and stamp-on-success would let an attacker against a failing endpoint force one fetch per backoff `B` instead of per cooldown `C` (unbounded with `B = 0`).

### S-07 concurrency — the cooldown must be re-checked under the lock (round-4 blocking finding)
A cooldown checked only *before* `get(force_refresh=True)` is a check-then-act race. N concurrent unknown-`kid` requests on an empty cache all call `get()`; the first fetches (holding `_refresh_lock`) while the others queue. When it completes, every waiter wakes, receives the newly cached keys, finds its `kid` absent, evaluates the cooldown against the **still-unadvanced** `_last_forced_refresh` (nobody has stamped yet — the stamp happens under the lock, and none of them has re-acquired it), passes, and queues its own forced refresh. Those then serialize on the lock and each fetches. Result: 1 initial + N forced fetches from N concurrent requests — the S-07 amplifier, now with a lock-shaped queue in front of it. The plan's sequential two-token test cannot see this.

**Why the in-lock re-check closes the window:** the stamp is written under `_refresh_lock`, so the only observation that can be ordered with respect to *every* stamp is one made under the same lock. A waiter that re-checks under the lock sees the stamp made by whichever forced caller acquired the lock before it, finds the cooldown active and an unexpired cache present (that caller's result), and returns it without fetching. Check-and-stamp are now atomic with respect to the lock; the pre-lock check is only a fast path that keeps on-cooldown callers off the lock. The order inside the lock is: (1) cache/cooldown re-check → return cache; (2) S-08 backoff gate → return unexpired cache or raise, no stamp; (3) stamp `_last_forced_refresh` if forced; (4) `_fetch()`.

**Measured on real code, not a model** (temporary spike of the full fix in `src/pmcp/auth.py`, reverted byte-identical afterwards; probe `test_s07_concurrent_unknown_kids_share_one_forced_refresh`, N=5, the initial fetch suspended on an `asyncio.Event` until all five requests were queued on the lock):
- current tree (no cooldown at all): `AssertionError: concurrent unknown kids amplified the refresh: fetches=6 (1 initial + 5 forced for 5 concurrent requests)`
- round-3 variant of the fix (cooldown checked only before the lock; in-lock re-check cache-only) — the `diff` against the spike was the single line `if self._serve_cache_instead(now, force_refresh=force_refresh):` → `if not force_refresh and self._cached(now) is not None:`; `git diff --stat` = `src/pmcp/auth.py | 65 +++...`: **same `fetches=6`** — the mutant *is* the planned fix and is red.
- fix with the in-lock re-check: passes, `fetches=2` (1 initial + exactly 1 forced, for N=5).

Residual, stated: a forced refresh queued behind a *non-forced* (TTL) refresh still fetches once more after it, because the TTL refresh does not stamp the forced-refresh cooldown. That is one extra fetch per window at most, and it also suppresses every other concurrent forced caller — so the amplifier bound (≤ 1 forced fetch per `C`) holds; it is not a hole.

**Why not the alternatives:**
- A **per-`kid` negative cache** does not stop the attack: the amplifier sends *random* `kid`s, each one unknown and absent from the negative cache, so each still forces a fetch.
- **Moving rate limiting ahead of auth** is insufficient and broad: rate limiting is per-IP and optional (only when `rate_limit_rpm > 0`), so it bounds nothing in the default config, and reordering changes semantics for every auth path.

**Failure mode when the cooldown trips:** an unknown `kid` arriving during an active cooldown is served the cached JWKS; `validate_resource_server_token` then raises `ResourceServerAuthError("invalid_token", "No matching JWK found.")` → `handle_mcp` returns **401** (`http.py:576`). The client retries; the next window's first unknown `kid` forces a fresh fetch.

**Cannot lock out a legitimate key rotation:** the *first* unknown `kid` in each window always forces one refresh, which picks up rotated keys. The cooldown only suppresses *additional* fetches within a short window (10 s ≪ the 300 s cache TTL), so a rotated key is picked up within one cooldown period at worst — strictly better than the existing TTL-bounded staleness. The only degraded case is a genuinely-new key arriving during a window whose one refresh already fired without it: a transient 401, self-healing on the next request after the window. This is the correct fail-closed direction (reject an unverifiable token), not a lockout.

### S-08 — total `ClientTimeout` on the fetch, PLUS a shared failure-backoff so the last of N waiters is bounded by ~1 timeout
A total `ClientTimeout` alone is necessary but **not sufficient** — it bounds each lock *holder*, not each *request*. With an empty/expired cache and a failing endpoint, waiter 1 holds the lock for one timeout, fails, and leaves no usable cache; waiter 2 then acquires the lock and starts its *own* fetch, and so on, so the last of N concurrent callers waits ~N×timeout before its 503. **Measured on the current tree** (simulating an already-timeout-bounded fetch: each attempt sleeps `FT=0.2 s` then fails, N=5): the gather took **1.004 s ≈ N×FT**. Two changes are therefore required.

**Decision (a) — total timeout.** Add `aiohttp.ClientTimeout(total=self._fetch_timeout_seconds)` (default 5 s) to the `ClientSession`/`get` in `_fetch`. Use **total**, not connect-only: the fetch already caps size (`max_bytes`) but a malicious endpoint can drip bytes under that cap or stall after connect, so only a total bound covers connect + header wait + body read. 5 s is generous for a well-behaved HTTPS JWKS endpoint (typically <500 ms).

**Decision (b) — shared failure-backoff window.** Add `refresh_failure_backoff_seconds: float = 5.0` and `self._last_refresh_failure: float = float("-inf")`. In `get()`, *inside* the lock and after the unexpired-cache re-check, if `time.monotonic() - self._last_refresh_failure < self._refresh_failure_backoff_seconds`: return the cache if it is present **and unexpired** (`now < self._expires_at` — this is the `force_refresh=True` path, which passes the cache re-check once its cooldown has expired), otherwise raise `ResourceServerJWKSUnavailable` **without** calling `_fetch()`. Wrap `_fetch()` so a `ResourceServerJWKSUnavailable` sets `self._last_refresh_failure = time.monotonic()` before re-raising (a success resets it to `-inf`). One caller performs the (timeout-bounded) fetch; the remaining N−1 acquire the lock in turn and short-circuit at once, so they do not stack fetches behind each other. **Critically, the backoff branch never advances `_last_forced_refresh`** (it did not fetch) — that is what keeps the two windows from coupling; see the composition subsection.

**The bound, stated as the claim:** with fetch timeout `T` and backoff `B`, the LAST of N concurrent callers on an empty/expired cache against a hanging endpoint returns in **≈ T + (N−1)·ε, i.e. ~one timeout — NOT N×T** (ε is the cost of acquiring the lock and raising). `B` need only exceed the time for the burst to drain (negligible); the default `B = 5 s` also throttles a subsequent retry storm. **What waiters 2..N receive during the window:** a `ResourceServerJWKSUnavailable` → `handle_mcp` returns **503** (`http.py:565-570`). A caller arriving after the window (`> B` since the last failure) performs a fresh fetch, so the backoff cannot wedge recovery.

**On timeout mechanics and the cache:** aiohttp raises `asyncio.TimeoutError`; `_fetch`'s `except Exception` re-raises it as `ResourceServerJWKSUnavailable`. `_jwks`/`_expires_at` are written only *after* a successful `_fetch`, and the lock is released by `async with`. There is **no serving of keys past their TTL**: the in-lock re-check returns the cache only while `now < self._expires_at` (i.e. still valid, not stale); once the cache is expired or empty and the refresh fails, waiters get a 503, never expired keys. (The earlier draft's phrase "serves stale-but-valid keys" was wrong — an unexpired cache is not stale, and expired keys are never served.)

### S-07 × S-08 composition — a backoff-rejected attempt must not consume a cooldown window
The round-3 review caught a real interaction. If `get_for_token` advances `_last_forced_refresh` *before* calling `get(force_refresh=True)`, an attempt that the S-08 backoff then rejects (no outbound fetch) still spends the S-07 cooldown window. With an **unexpired** cached JWKS holding the old keys:

```
t=0    unknown-kid forces a refresh; endpoint down
t≈T    fetch times out; _last_refresh_failure stamped -> backoff until ≈T+B
        (endpoint actually recovers shortly after T)
t=C    cooldown elapsed; an unknown-kid request forces again and, if the stamp
        is taken before the call, advances _last_forced_refresh -> but backoff
        rejects the fetch. The window is spent with no fetch.
t=C..  callers keep validating against the OLD cached keys; the rotated key is
        not picked up until the NEXT cooldown window, ~one C later than it should be.
```

So a rotated key is rejected for up to one extra cooldown `C` beyond backoff expiry — **but only when the backoff outlasts the cooldown**, i.e. when `d + B > C` for a failed fetch of duration `d` (the backoff-rejected forced attempt at `t = C` exists only if backoff is still active then). With the defaults `C = 10, B = 5, T = 5` the two windows end together for a full timeout (`d = T`: `d + B = 10 = C`) and the backoff ends first for anything faster, so the composition bug is **latent at the defaults** and bites for any configuration with `B + T > C` (e.g. `C = 5` with the default `B`/`T`, or a longer `T`). It is still fixed here because the fix costs nothing and the windows are operator-tunable.

**Fix:** advance `_last_forced_refresh` **only when a fetch is actually attempted** — i.e. inside `get()`, past the backoff gate, immediately before `_fetch()` — never on the backoff-rejected branch (which returns the unexpired cache or raises without touching the stamp). A backoff-suppressed attempt then costs nothing, so the next forced attempt after backoff expiry fetches and picks up the rotated key.

**Worst-case rotation-recovery time, with the arithmetic (round-4 correction — the previous "≈ B + T, independent of C" claim was wrong).** Let a forced fetch start at `t = 0` and fail after `d` (`d ≈ 0` for an immediate refusal, `d = T` for a timeout); it stamps `_last_forced_refresh = 0` and `_last_refresh_failure = d`. The next forced fetch needs both `t ≥ C` (cooldown) and `t ≥ d + B` (backoff), so it is eligible at `t = max(C, d + B)` after the attempt began — equivalently `max(C − d, B)` after the failure — and the rotated key is accepted once that fetch finishes, after its own duration `T'` (`T' ≤ T`; ~0.5 s for a healthy HTTPS endpoint, `T` at worst). **Recovery = `max(C, d + B) + T'`**, so `C` still governs whenever `C − d > B`:
- **Endpoint fails immediately (`d ≈ 0`), then recovers:** eligible at `max(10, 0 + 5) = 10 s` — backoff expired at 5 s but the cooldown the failed attempt consumed holds until 10 s — then `+ T'`: **≈ 10.5 s typical, 15 s worst case (`T' = T`)**. Not ~10 s.
- **Endpoint times out (`d = T = 5`), then recovers:** eligible at `max(10, 5 + 5) = 10 s`, `+ T'`: **the same ≈ 10.5–15 s** — the same number only because the defaults sit exactly on the `C = B + T` boundary, not because recovery is independent of `C`.
- **Endpoint healthy, attacker consumed the window** (a successful forced fetch at `t = 0` that missed the rotation): the first legitimate rotated-`kid` request at `t ≥ C` forces a fetch, and the key is accepted after it: **≤ C + T'** from the attacker's fetch — **≈ 10.5 s typical, 15 s worst case**. The attacker cannot extend this: whichever caller's unknown `kid` triggers the `t = C` fetch, the fetch returns the same rotated JWKS. This is the accepted global-cooldown trade-off, far under the 300 s TTL and self-healing.
- **Buggy stamp-on-rejection variant, for comparison:** adds one further `C` only when `d + B > C` (see above); at the defaults it adds nothing, which is why the recovery test below uses the default relationship (`C > B`) to pin the bound and a *separate* test uses `B > C` to pin the composition fix. The round-3 model used `C = 0.4, B = 0.5` — a backoff that outlasts the cooldown — which is exactly the configuration that hides the `C` dependence.

**Measured on real code** (the same spike, fake clock via `monkeypatch.setattr("pmcp.auth.time", SimpleNamespace(monotonic=clock))`, unexpired cache holding only the OLD key, endpoint down at `t = 0` and recovered right after the failure):
- `test_s07_s08_recovery_after_failed_forced_refresh_waits_out_the_cooldown[immediate|timeout]` (`C = 10, B = 5`, `d ∈ {0, 5}`): asserts **no fetch at `t = 9`** (backoff over in the immediate case; cooldown not) and **fetch + rotated key accepted at `t = 10`**. Current tree (no windows): `AssertionError: a forced fetch ran at t=9.0s, before max(C, d+B)=10.0s: fetches=2` for both parametrizations. Stamp-on-success-only variant of the fix (stamp moved after a successful `_fetch()`; `git diff --stat` = `src/pmcp/auth.py | 63 ...`): the **`[immediate]`** case is red with the same message and `[timeout]` stays green — the default relationship is what exposes it. Fixed spike: both pass with `fetches == 2` at `t = 10`.
- `test_s07_s08_backoff_rejection_does_not_consume_the_cooldown` (`C = 0.4, B = 0.5`, `d = 0`): current tree red (fetches at `t = 0.45`, no backoff); the stamp-on-rejection variant (two lines added to the backoff branch: `if force_refresh: self._last_forced_refresh = now`; `git diff --stat` = `src/pmcp/auth.py | 67 ...`) is red with `AssertionError: rotated key not accepted at backoff expiry: fetches=1`; fixed spike passes with `fetches == 2` at `t = 0.55`.

### S-10 — return a non-Host-derived (operator-configured) `resource`, not "reject the Host outright"
**Decision:** stop deriving `resource` from the request. Compute a canonical resource from operator config in the app closure and return it verbatim: `resource_server_audience` when set (the RFC 8707 canonical identifier, and the exact value tokens are validated against), else the origin of the operator-configured metadata URL, else `""`. Never touch `request`. For the fallback, parse the **normalized** `auth_metadata.protected_resource_metadata_url` (already run through `normalize_auth_metadata`, not the raw kwarg) and take the origin from its `netloc`: `f"{p.scheme}://{p.netloc}/mcp"`. The normalized value is what `sanitize_public_auth_url` returns, which is `redact_auth_url(url)` — and that rebuilds the netloc from `hostname`/`port` only (userinfo dropped) and re-brackets an IPv6 literal (`auth.py:104-108`). So the normalized `netloc` already carries the no-userinfo property the round-3 note wanted, **and** stays valid for IPv6. Rebuilding again from `p.hostname`/`p.port` in `http.py` — the round-3 wording — is wrong for a literal IPv6 metadata URL because `hostname` strips the brackets (grok round-4 note). Measured on the real normalizer: for `https://[2606:4700::1]:8443/.well-known/oauth-protected-resource` the hostname rebuild gives `https://2606:4700::1:8443/mcp` (invalid), the normalized `netloc` gives `https://[2606:4700::1]:8443/mcp`; for `https://op:secret@issuer.example/...?token=abc` both give `https://issuer.example/mcp` (the normalized URL is `https://issuer.example/.well-known/oauth-protected-resource?token=%5BREDACTED%5D`, userinfo already gone).

**Why not "reject a disallowed Host outright" (call `_host_rejected`):** `_host_rejected` returns `False` whenever `allowed_origins is None`, which is the local-first default. So reject-outright would still reflect the attacker Host in the default configuration — it fails open exactly where it matters. Returning an operator-configured value fixes S-10 unconditionally, in every config.

**What #211 constrains, and how this respects it:** the endpoint must never advertise an attacker-supplied value as though PMCP stands behind it — advertising an attacker-supplied Host as the vouched `resource` is precisely the "we verified this" implication #211 removed for server-supplied URLs. This fix is *stronger* than #211's relay-but-mark-unverified remedy: because the endpoint has its own operator-configured canonical resource, it simply never emits the untrusted value, so there is no unverified attacker value to mark and no "verified" claim is reintroduced. It also aligns the metadata endpoint with the existing `SECURITY.md:34-36` promise that the canonical resource "is never derived from the request Host header." **This is an inconsistency in spirit only, NOT a violation of the frozen ledger claim** (settled independently by the grok and gemini reviewers): that sentence is scoped specifically to *token audience binding* — `_resource_audience()` returns `resource_server_audience or ""` and is what tokens are validated against — whereas the metadata endpoint's `resource` is a *separate publication* the claim does not cover. The token path already honors the claim; the metadata path publishes a different, Host-derived value, which does not falsify the audience claim but does read as inconsistent with its intent. The fix removes that divergence. **The endpoint is allowed to imply:** "the operator configured this resource identifier." **It must not imply:** anything about an attacker-supplied Host — it must not echo it at all.

This bounds the last of N concurrent waiters to ~one timeout, bounds N concurrent unknown-`kid` requests to one forced fetch, and keeps the cooldown from being consumed by a backoff-rejected attempt. (S-07 + S-07 concurrency + S-08 decision (b) + composition fix)
