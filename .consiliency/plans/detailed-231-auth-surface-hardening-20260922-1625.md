# Detailed plan: harden the HTTP auth surface — JWKS amplifier (S-07), JWKS fetch timeout (S-08), metadata Host reflection (S-10)

## Task
Fix the remainder of the 2026-09-01 codebase review finding tracked in Consiliency/pmcp#231: three defects on the HTTP auth surface (the gateway's trust boundary), where the dangerous direction is failing OPEN.

- **S-07** — unauthenticated outbound-fetch amplifier: an unknown `kid` forces an outbound JWKS refresh with no cooldown, and rate limiting runs *after* auth, so an unauthenticated caller drives repeated outbound fetches with random `kid`s.
- **S-08** — the JWKS fetch has no `ClientTimeout` and runs while holding `_refresh_lock`, so a slow/hanging JWKS endpoint stalls every request coroutine waiting on that lock (an async hang under the lock, not a synchronously blocked event loop). Worse, a *failed* refresh leaves no usable cache, so waiters acquire the lock in turn and each re-attempt the fetch — N concurrent callers time out sequentially and the last waits ~N×timeout.
- **S-10** — the OAuth protected-resource-metadata endpoint returns a Host-derived `resource` and its route never checks the Host allowlist, so a request with an attacker-supplied `Host` gets that Host advertised back as the resource.

S-09 is already fixed and merged in #281 — out of scope here.

## Research summary
All three findings were confirmed by reading the current tree at commit `af67207` (branch `plan/231-auth-surface`).

- `AsyncJWKS` lives in `src/pmcp/auth.py`: `__init__` at `auth.py:380`, `get()` at `auth.py:401` (double-checked locking on `_refresh_lock`), `get_for_token()` at `auth.py:414` (calls `self.get(force_refresh=True)` at `auth.py:421` for any unknown `kid`), `_fetch()` at `auth.py:424` (opens `aiohttp.ClientSession()` at `auth.py:426` with **no** `ClientTimeout`). `get()` holds `_refresh_lock` (acquired `auth.py:405`) across the whole `_fetch()` call.

So the amplifier is reachable pre-rate-limit, unauthenticated.

Its route is registered at `http.py:743-750`, only when `auth_metadata.protected_resource_metadata_url` is set, and never calls `_host_rejected`. `_host_rejected` (`http.py:388`) returns `False` when `allowed_origins is None` (the local-first default), and `_resource_audience()` (`http.py:405`) returns `resource_server_audience or ""`.
- **#211 (`56a555c` "fix(auth): stop vouching for URLs a downstream server supplied")** touched `auth.py`, `SECURITY.md`, `CHANGELOG.md` and `tests/test_auth.py` — it did **not** touch the metadata handler; the Host-derived `resource` predates it (introduced in the AUTHRS commit `3c2ad0b`). #211 is therefore a *principle* constraint, not a code overlap. Separately, `SECURITY.md:34-36` already asserts the token audience "is bound to the operator-configured canonical resource URI (`resource_server_audience`, per RFC 8707) and is never derived from the request Host header." The metadata endpoint's Host-derived `resource` violated the spirit of that same principle.
- Test harness: `tests/test_auth.py` tests `AsyncJWKS` by monkeypatching `jwks._fetch` and counting calls (`test_async_jwks_caches_and_coalesces_fetches:374`, `test_async_jwks_unknown_kid_forces_one_refresh:396`). `tests/test_transport_http.py` builds the app via a `_make_app` helper (patches `StreamableHTTPSessionManager`) and drives it with a Starlette `TestClient` (`test_well_known_protected_resource_metadata_is_public:169`).

## Design decisions (made explicitly)

### S-07 — global forced-refresh cooldown (not a per-kid negative cache, not reorder-before-auth)
**Decision:** add a per-`AsyncJWKS` cooldown that bounds *forced* refreshes to at most one per window (default 10 s). `get_for_token` only calls `get(force_refresh=True)` when `time.monotonic() - self._last_forced_refresh >= self._forced_refresh_cooldown_seconds`. During the cooldown an unknown `kid` returns the currently-cached JWKS (no outbound fetch). **The cooldown timestamp is advanced inside `get()`, only when a fetch is actually attempted (past the S-08 backoff gate) — not before the call in `get_for_token`.** Stamping before the call is the composition bug the round-3 review caught: see "### S-07 × S-08 composition" below.

**Why not the alternatives:**
- A **per-`kid` negative cache** does not stop the attack: the amplifier sends *random* `kid`s, each one unknown and absent from the negative cache, so each still forces a fetch.
- **Moving rate limiting ahead of auth** is insufficient and broad: rate limiting is per-IP and optional (only when `rate_limit_rpm > 0`), so it bounds nothing in the default config, and reordering changes semantics for every auth path.

**Failure mode when the cooldown trips:** an unknown `kid` arriving during an active cooldown is served the cached JWKS; `validate_resource_server_token` then raises `ResourceServerAuthError("invalid_token", "No matching JWK found.")` → `handle_mcp` returns **401** (`http.py:576`). The client retries; the next window's first unknown `kid` forces a fresh fetch.

**Cannot lock out a legitimate key rotation:** the *first* unknown `kid` in each window always forces one refresh, which picks up rotated keys. The cooldown only suppresses *additional* fetches within a short window (10 s ≪ the 300 s cache TTL), so a rotated key is picked up within one cooldown period at worst — strictly better than the existing TTL-bounded staleness. The only degraded case is a genuinely-new key arriving during a window whose one refresh already fired without it: a transient 401, self-healing on the next request after the window. This is the correct fail-closed direction (reject an unverifiable token), not a lockout.

### S-08 — total `ClientTimeout` on the fetch, PLUS a shared failure-backoff so the last of N waiters is bounded by ~1 timeout
A total `ClientTimeout` alone is necessary but **not sufficient** — it bounds each lock *holder*, not each *request*. With an empty/expired cache and a failing endpoint, waiter 1 holds the lock for one timeout, fails, and leaves no usable cache; waiter 2 then acquires the lock and starts its *own* fetch, and so on, so the last of N concurrent callers waits ~N×timeout before its 503. **Measured on the current tree** (simulating an already-timeout-bounded fetch: each attempt sleeps `FT=0.2 s` then fails, N=5): the gather took **1.004 s ≈ N×FT**. Two changes are therefore required.

**Decision (a) — total timeout.** Add `aiohttp.ClientTimeout(total=self._fetch_timeout_seconds)` (default 5 s) to the `ClientSession`/`get` in `_fetch`. Use **total**, not connect-only: the fetch already caps size (`max_bytes`) but a malicious endpoint can drip bytes under that cap or stall after connect, so only a total bound covers connect + header wait + body read. 5 s is generous for a well-behaved HTTPS JWKS endpoint (typically <500 ms).

**Decision (b) — shared failure-backoff window.** Add `refresh_failure_backoff_seconds: float = 5.0` and `self._last_refresh_failure: float = float("-inf")`. In `get()`, *inside* the lock and after the unexpired-cache re-check, if `time.monotonic() - self._last_refresh_failure < self._refresh_failure_backoff_seconds`: return the cache if it is present **and unexpired** (`now < self._expires_at` — this is the `force_refresh=True` path, whose caller skipped the top re-check), otherwise raise `ResourceServerJWKSUnavailable` **without** calling `_fetch()`. Wrap `_fetch()` so a `ResourceServerJWKSUnavailable` sets `self._last_refresh_failure = time.monotonic()` before re-raising (a success resets it to `-inf`). One caller performs the (timeout-bounded) fetch; the remaining N−1 acquire the lock in turn and short-circuit at once, so they do not stack fetches behind each other. **Critically, the backoff branch never advances `_last_forced_refresh`** (it did not fetch) — that is what keeps the two windows from coupling; see the composition subsection.

**The bound, stated as the claim:** with fetch timeout `T` and backoff `B`, the LAST of N concurrent callers on an empty/expired cache against a hanging endpoint returns in **≈ T + (N−1)·ε, i.e. ~one timeout — NOT N×T** (ε is the cost of acquiring the lock and raising). `B` need only exceed the time for the burst to drain (negligible); the default `B = 5 s` also throttles a subsequent retry storm. **What waiters 2..N receive during the window:** a `ResourceServerJWKSUnavailable` → `handle_mcp` returns **503** (`http.py:565-570`). A caller arriving after the window (`> B` since the last failure) performs a fresh fetch, so the backoff cannot wedge recovery.

**On timeout mechanics and the cache:** aiohttp raises `asyncio.TimeoutError`; `_fetch`'s `except Exception` re-raises it as `ResourceServerJWKSUnavailable`. `_jwks`/`_expires_at` are written only *after* a successful `_fetch`, and the lock is released by `async with`. There is **no serving of keys past their TTL**: the in-lock re-check returns the cache only while `now < self._expires_at` (i.e. still valid, not stale); once the cache is expired or empty and the refresh fails, waiters get a 503, never expired keys. (The earlier draft's phrase "serves stale-but-valid keys" was wrong — an unexpired cache is not stale, and expired keys are never served.)

### S-07 × S-08 composition — a backoff-rejected attempt must not consume a cooldown window
The round-3 review caught a real interaction. If `get_for_token` advances `_last_forced_refresh` *before* calling `get(force_refresh=True)`, an attempt that the S-08 backoff then rejects (no outbound fetch) still spends the S-07 cooldown window. With an **unexpired** cached JWKS holding the old keys:

```
t=0    unknown-kid forces a refresh; endpoint down
t≈T    fetch times out; _last_refresh_failure stamped -> backoff until ≈T+B
        (endpoint actually recovers shortly after T)
t=C    cooldown elapsed; an unknown-kid request forces again and, if the stamp
        is taken before the call, advances _last_forced_refresh -> but backoff
        rejects the fetch. The window is spent with no fetch.
t=C..  callers keep validating against the OLD cached keys; the rotated key is
        not picked up until the NEXT cooldown window, ~one C later than it should be.
```

So a rotated key is rejected for up to one extra cooldown `C` beyond backoff expiry, and a longer fetch timeout widens the overlap — breaking the "picked up within one window" property that motivated choosing a global cooldown over a per-`kid` cache.

**Fix:** advance `_last_forced_refresh` **only when a fetch is actually attempted** — i.e. inside `get()`, past the backoff gate, immediately before `_fetch()` — never in `get_for_token`, and never on the backoff-rejected branch. A backoff-suppressed attempt then costs nothing, so the next forced attempt after backoff expiry fetches and picks up the rotated key.

**Worst-case rotation-recovery time, as numbers (defaults `C=10 s`, `B=5 s`, `T=5 s`):**
- **Endpoint was failing, then recovers:** the rotated key is accepted at the first forced attempt after the failure-backoff expires — **≈ B + T (~10 s) from the last failed fetch, independent of `C`**. (The buggy stamp-before design added up to one extra `C`, i.e. ~20 s.)
- **Endpoint healthy, attacker just consumed the window:** a legitimate rotation may wait out at most one cooldown — **≤ C (~10 s)**. This is the accepted, pre-existing global-cooldown trade-off (an attacker can delay a rotation's pickup by ≤ C by forcing a successful fetch just before it), far under the 300 s TTL and self-healing.

**Verified with an executable model of both designs** (fake clock, `C=0.4 s`, `B=0.5 s`; endpoint down at t=0, recovers immediately after): the stamp-**before** variant did **not** accept the rotated key at backoff expiry (t=0.5) — `rotated_key_accepted=False, fetches=1` — while the stamp-**on-fetch** variant did — `rotated_key_accepted=True, fetches=2`. The current tree has neither mechanism, so this composition mutant is the *buggy variant of the fix itself*; the acceptance test (below) reproduces it and is red against it.

### S-10 — return a non-Host-derived (operator-configured) `resource`, not "reject the Host outright"
**Decision:** stop deriving `resource` from the request. Compute a canonical resource from operator config in the app closure and return it verbatim: `resource_server_audience` when set (the RFC 8707 canonical identifier, and the exact value tokens are validated against), else the origin of the operator-configured metadata URL, else `""`. Never touch `request`. For the fallback, parse the **normalized** `auth_metadata.protected_resource_metadata_url` (already run through `normalize_auth_metadata`, not the raw kwarg) and rebuild from `p.hostname`/`p.port`, **not** `p.netloc`: `f"{p.scheme}://{p.hostname}" + (f":{p.port}" if p.port else "") + "/mcp"`. Using `hostname`/`port` structurally drops any `user:pass@` userinfo so operator-supplied credentials can never surface in the published `resource` (grok round-3 note).

**Why not "reject a disallowed Host outright" (call `_host_rejected`):** `_host_rejected` returns `False` whenever `allowed_origins is None`, which is the local-first default. So reject-outright would still reflect the attacker Host in the default configuration — it fails open exactly where it matters. Returning an operator-configured value fixes S-10 unconditionally, in every config.

**What #211 constrains, and how this respects it:** the endpoint must never advertise an attacker-supplied value as though PMCP stands behind it — advertising an attacker-supplied Host as the vouched `resource` is precisely the "we verified this" implication #211 removed for server-supplied URLs. This fix is *stronger* than #211's relay-but-mark-unverified remedy: because the endpoint has its own operator-configured canonical resource, it simply never emits the untrusted value, so there is no unverified attacker value to mark and no "verified" claim is reintroduced. It also aligns the metadata endpoint with the existing `SECURITY.md:34-36` promise that the canonical resource "is never derived from the request Host header." **This is an inconsistency in spirit only, NOT a violation of the frozen ledger claim** (settled independently by the grok and gemini reviewers): that sentence is scoped specifically to *token audience binding* — `_resource_audience()` returns `resource_server_audience or ""` and is what tokens are validated against — whereas the metadata endpoint's `resource` is a *separate publication* the claim does not cover. The token path already honors the claim; the metadata path publishes a different, Host-derived value, which does not falsify the audience claim but does read as inconsistent with its intent. The fix removes that divergence. **The endpoint is allowed to imply:** "the operator configured this resource identifier." **It must not imply:** anything about an attacker-supplied Host — it must not echo it at all.
